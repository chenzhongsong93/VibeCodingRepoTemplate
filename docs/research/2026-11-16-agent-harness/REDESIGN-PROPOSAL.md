## 1. 对原方向的明确裁决

用户要的是能支撑中大型系统长期演进的仓内研发环境：**找到当前唯一设计来源，按所属功能域演进设计和实现，使长期知识持续收敛，同时限制过程稿、设计副本和无依据代码扩张。**

原方案主动把域规格改成可选能力、把Spec Kit集成留到未来，将每任务共享JSON/Markdown及检查内核置于中心。实现随后完成了安全装配、UUID任务、检查状态、指纹和升级，却没有建立完整设计治理。这是方案取向错误，不只是说明过短或少几个模板。外部平台依赖限制也被错误扩大成了不必真正集成两套方法。

直接反例：当前`project.mjs`的默认minimal/standard输出没有系统设计及任何spec，product的documents/完整性集也不要求域规格；`tests/v2/tasks.test.mjs`的TASK-06以空域引用、通用阶段note、验收映射core.policy和HANDOVER完成全生命周期。143项既有测试通过只能证明其定义的工具行为，不能证明核心目标完成。

刚创建的`docs/implementation/design-authority-correction/DESIGN.md`同样撤为待替代草稿：它虽识别权威问题，仍过早设计注册表、自动域绑定、hash/disposition门禁；也没有证明默认给每个生成项目建立治理域是必要的。**接下来不按这份补丁草稿写代码。**

## 2. 必须作为整体吸纳的工程模型

```mermaid
flowchart LR
 P[政策与授权] --> S[系统设计和所属域]
 S --> R[规范化需求与验收]
 R --> D[方案与测试设计]
 D --> I[实现及运行证据]
 I --> C[对照目标判定偏差]
 C --> K[回刷同一长期权威]
 K --> H[短交接与未闭环]
 H --> S
 C -->|设计不可行或范围改变| R
```

闭环中的关键联系不可拆开：

- 入口连接宪法、规则、当前设计与工作状态；只有简短入口而没有下层体系只是索引壳。
- 需求连接来源、系统约束、域设计、可验证验收、测试与证据；单独有spec标题不能约束实现。
- 系统总体设计与域详细设计共同存在；只维护任务会失去整体，只维护架构图不足以指导具体行为。
- 活规格连接明确的批准和实现状态；就地更新不等于把未实现内容写成已交付事实。
- 过程稿不入长期源码层，同时必须把决策、验收口径和未完成条件提炼到规定归宿；不能用“忽略草稿”换失忆，也不能为续接永久复制全部计划。
- 完成判断连接行为证据、设计一致性审查、必要真实环境和知识回刷；机器结构检查只能证明其覆盖范围。
- Harness自身的规则、技能、模板、实现和检查也接受这套治理，不能靠不断追加补丁和口号维持。

## 3. 目标、非目标与完整性底线

### 目标

1. 新会话可从仓内找到当前系统与域设计，知道谁负责哪类决定；无需猜哪份历史设计最新。
2. Spec Kit组织规范链，superpowers提供方法和执行质量；两者共用同一套权威及过程产物。
3. `specs/NNN-<domain>/spec.md`是长期维护的特性功能设计。同域变更在同一文档就地演进；职责独立的新域才新增域目录。
4. 每次变更都能说明改变哪些需求、约束、结构/流程、契约和验收；超出批准范围先重新分析，不能因Agent想到新抽象就扩服务、表或模块。
5. 代码与设计偏差有发现、裁决、实施、验证和回刷路径；完成后知识有唯一归宿。
6. 源码知识层不随变更次数持续增加一套套spec/plan/tasks/implementation报告；保留必要追溯和中断恢复。
7. 保留模板多语言、命名、多仓、产品/PI及安全装配等已有价值，使工具服从上述目标。

### 非目标

不复制AWB业务、算子规则、数据库、实际API文档、采集/导入脚本或发布地址；不新增平台/扫描服务依赖；不宣称已vendoring外部Spec Kit/superpowers实现；不建设新的通用工作流平台；不把自然语言语义正确性伪装成机器可证明。不在本轮删除、移动、归档历史或创建Git提交。

### 底线

小项目可以减篇幅、合并非冲突内容、标明不适用；不能关闭设计权威或通过去掉规范链降级。编号、行数、图工具和目录名可以适配，**长期职责、唯一来源、同域演进和收敛义务不能适配掉。**

## 4. 政策、设计、事实与历史分别如何权威

政策优先级与知识职责不是同一张排序表。项目内部宪法约束AGENTS和rules；用户/宿主指令始终更高。系统设计负责公共边界，域设计负责本域细节，专门契约/模型负责对应字段真相；不能因为某文档“层次高”就复制或覆盖另一职责的正文。

| 载体/新仓建议归属 | 唯一职责 | 更新方式与禁止事项 |
|---|---|---|
| `.specify/memory/constitution.md` | 文档唯一归宿、设计/事实状态、风险授权、追溯、验证和上下文等项目不变量 | 重大治理变更显式裁决；不存业务详细设计，不自称高于用户 |
| `AGENTS.md` + 平台薄入口 | 公共政策摘要、适用规则、续接路径、设计地图、工作流入口 | 不堆目录树、端点数和流水账；不把配置或平台文件变成第二政策 |
| `docs/rules/` | 开发、文档、测试、提交、行为、代码质量的执行约束 | 解释含义和判据；避免另造独立流程顺序或重复权威正文 |
| 产品/战略/远期目标 | 目标用户、价值、非目标、战略与能力方向 | 保留现有可选产品资产；不能把远期目标冒充已实现系统事实 |
| `docs/00-system/` | 系统总体设计：目标/非目标、边界、域划分、公共不变量、协作、质量与运行/演进 | 跨域或公共机制变化才触发对应更新；不重写全部域细节 |
| `specs/NNN-<domain>/spec.md` | 域长期特性功能设计：需求/验收、结构、行为、失败语义、决策、红线与挂起项 | 同域就地更新、长期维护；不是需求卡、任务日志或交付后的知识笔记 |
| `docs/02-design/`中的明确专门资产 | 当前契约、数据/接口事实与长期测试回归资产等；逐类声明source与派生关系 | 一字段一个权威；不作任意设计草稿的存放箱；API-first/code-first按项目选择 |
| `docs/ledger/` | 问题、债务、错误学习、版本与未闭环追溯 | 根因/预防回到测试、规则或所属设计；不再展开另一套设计正文 |
| `docs/HANDOVER.md` | 当前阶段、活跃变化、全部未闭环、必要决策/证据定位与下一步 | 保持短；长期设计用指针；不能仅靠本机草稿才能恢复 |
| 域内`plan/`、`tasks/`、`implement/`等过程材料 | 本次执行方案、依赖、操作步骤、详细报告和临时证据 | 默认本地忽略，不持续进入源码；长期有价值内容收敛到上述owner；两套方法共用同一份工件 |
| Git历史及已有历史区 | 历史交付与决策版本的追溯 | 不作为当前设计来源；本轮无提交/清场授权，不能假定未提交草稿已被Git保存 |
| `.harness/project.json`及工具 | 可用能力、路径、命令、执行状态等机器辅助 | 不是业务设计或批准意图的权威。注册唯一、文件hash变化均不能证明设计正确 |

已有仓先按职责映射现有路径，不能同时生成新正文又把旧正文继续当权威。当前`02-design/system-architecture.md`、`entity-model.md`若承担系统/共享模型，应先确认承接内容和引用，再决定保留路径或迁为单一正文+兼容指针。迁移和删除单独给清单，不自动执行。

## 5. 系统与域模板：必须能写出真实设计

系统模板至少包括：范围和非目标、关键场景、系统上下文、域/子系统职责、公共不变量及依赖方向、跨域流程和失败语义、共享数据/契约权威、部署/质量属性、兼容演进、重大决策和已知差距。每个域都能说明服务哪个系统场景，公共约束在哪里定义。

域模板采用“元信息+完整内容结构”，放在`docs/guides/living-spec-template.md`，避免把模板当成specs下另一份特性设计：

| 内容 | 要求 |
|---|---|
| 元信息与状态 | 域身份、职责、批准/变更来源、当前设计版本；区分待实现/已验证，不只写一个Accepted |
| 目标、非目标和质量目标 | 有边界和可衡量目标，避免需求无限延展 |
| 约束与环境 | 引用适用宪法/系统约束及真实环境；不复制公共规则 |
| 上下文与边界 | 上下游、输入/输出、职责及跨域关系，必要图示 |
| 需求与验收 | FR/SHALL、GWT场景、成功标准、真实测试/证据锚点 |
| 软件结构 | 组件职责、依赖方向、公开/内部边界；目标结构与现存实现标清 |
| 关键流程 | 核心协作、状态、并发/异步、异常及恢复语义；图与正文一起维护 |
| 数据/接口与运行 | 指向共享权威；只写本域特殊约束，避免字段/部署双写 |
| 决策沿革 | 日期、来源、决策与被否决备选理由、生效/取代关系；实质性决策留痕 |
| 红线与陷阱 | 约束及事故/测试来源，而非无限追加口号 |
| 开放项和关联域 | 未实现/未验证/挂起去向，废弃域明确接管域，不靠删除历史掩盖 |

每节模板说明写到什么程度、何时只引用、何时可标不适用；不能只给栏目标题。首个试点须有填实的系统设计与至少两个域的成品，先证明能指导改动，再提炼检查规则。模板维护仓自身优先作为真实样本，不给所有生成项目强塞一个“repo-governance业务域”。

## 6. 设计的时间语义与反膨胀

- 拟议方案可在本地过程工件中展开；批准前不得悄悄替换当前已接受目标。
- 规格/方案获批后，成为**同一域活规格**的可追溯目标修订，明确待实现/待验证状态；不能等到任务结束才第一次回写，让task临时充当正式设计。
- 实施前记录要实现的目标版本与来源；实现发现不成立时回到裁决。不能把基线重新定义成“当前文件正好是什么”来抹平偏差。
- converge核对实现与已批准目标，更新实现/验证状态、真实结构和事实资产，并把长期决策提炼回对应位置。变化超出原批准目标要说明新的裁决。
- 同域后续变化继续编辑同一文档。只在职责拆分/合并/新增独立能力域时新增域，记录接管关系。不是按一次需求、一次会话或版本号创建新权威。
- plan/tasks/implement及重型执行日志默认不入长期源码层。不能默认每任务永久保存一套task.md、设计备选和实现报告，并称其为共享设计记忆。
- 同机续接可读取本地过程材料；换机/新检出只承诺恢复已共享的正式设计、当前变更摘要与未完成条件。缺本地草稿明确重建，不假装Git保留了它。
- 为协作确需共享的执行材料，应限定为当前活跃变化、有明确用途和结束处理方式；不能自动升级成长期设计来源。是否采用单独短变更记录由试点决定，不先强制UUID协议。
- “只追加决策”不等于固定篇幅永远不变：保留实质决策和取代关系，复杂必要内容可留域内附件并由spec索引。不硬套110–220行，不自动删除沿革。

## 7. Spec Kit与superpowers的完整编排

默认e2e工作流必须存在。`dev-conductor`、项目`dev-flow`和平台入口导向同一正文，不各自维护生命周期。Spec Kit提供规范化动作和阶段关系，superpowers提供探索、计划、TDD、调试、审查和验证方法。方法调用共享同一组工件，不分别输出一套长期文档。

| 阶段 | 读取和方法职责 | 产物及落点 | 退出/回退依据 |
|---|---|---|---|
| 开工定向/宪法检查 | 读AGENTS、宪法、HANDOVER、系统和所属域；检索现有实现及调用方/环境变体，判风险和授权 | 本次范围、来源、非目标、受影响域/公共边界；过程记录本地 | 找不到权威或存在未裁决目标冲突，先处理依赖问题，不盲目写码 |
| specify/clarify | 先查复用域；Spec Kit规范化FR/GWT/SC，superpowers brainstorming辅助澄清、方案探索和选择 | 所属域设计的可审阅修订；未批准细稿本地，获批目标归同一活spec | 需求可测试、来源明确、范围受限；既有批准可复用，不逐项重复询问 |
| plan + tasks + TEST-DESIGN | Spec Kit组织技术方案/任务依赖；superpowers writing-plans完善同一份执行计划。因子→场景→边界/异常→用例→覆盖矩阵 | 体系/域设计中的必要结构与取舍；本地plan/tasks带验证命令；长期回归设计进入专门测试资产 | DUAL-REVIEW：需求对照与测试覆盖对照；关键架构/测试缺口解决后才实施 |
| analyze | 实施前独立检查需求—系统约束—域设计—计划—测试覆盖及术语 | 缺口、冲突和处置；不另建永久设计副本 | 已处理必需一致性缺口；语义判断不伪装成脚本通过 |
| implement | 单一e2e编排调用执行/TDD；失败用systematic-debugging，关键变化做code review | 代码、测试、局部执行证据；发现范围/设计问题回规格或计划 | 不是task勾选完就算完成；每任务验证其内联标准 |
| verify | superpowers verification-before-completion与项目本地命令；按风险/影响覆盖L层及必要真实环境 | 命令、范围、输入版本、退出、实际结果/未运行和失败解释 | 结构、行为、环境、语义分别结论；测试通过不覆盖设计冲突 |
| converge | Spec Kit收敛动作对照成功标准；检查目标/实现偏差、回刷路由、长期知识及遗留 | **原系统/域设计就地修订**，契约/模型/测试资产再生或更新，决策沿革，bugs/debt/未完成去向 | 必需验收和设计审查满足，机器覆盖部分通过；未收敛不假称done |
| handover | 按短续接模型整理当前态、全部未闭环和下一步 | HANDOVER及必要当前变更摘要；不复制长期设计 | 新会话能从正式设计续接；开发完成不自动授权Git或发布 |
| release/外部动作 | 仅命中且明确授权时进入；项目适配提供真实命令、回滚、版本/产物关联 | 分别记录开发/集成/发布/部署证据 | 不复制AWB平台，不使用缺实现命令；不能以本地绿称已发布 |

源仓ANALYZE顺序等漂移未被裁决；上表将实施前一致性与实施后验收复核分开，是针对模板的目标契约。

### 工具适配必须经过真实核对

源码定义了调用关系，不证明本机安装和产物行为。实施时必须核对实际可用的Spec Kit/superpowers版本、触发方式、默认目录和覆盖方式，验证同域重入不会新建另一份权威。不能仅在文案写“覆盖默认落点”。

完整集成路径有工具时真实调用；无工具路径明确报告未调用，并按仓内同等规范/测试/评审工作交付。两条路径都保留上述义务，不将规范化弱化成自由发挥。不自动下载安装，不引入AgentCenter/扫描或其他平台服务。若某工具无法按项目产物契约适配，记录其限制并阻断该集成声明，不假装成功。

## 8. 应吸纳的机制范围和证据边界

完整范围不止用户举例：入口/政策与授权、系统和域分层、稳定域身份与完整模板、图与关系维护、目标/事实裁决、过程反膨胀、派生物分类与再生一致性、影响面/环境勘察、测试设计/TDD/追溯、真实边界证据、converge回刷/遗留、门禁自证/真实接入、跨平台和续接、缺陷/债务学习、版本发布分离、技能/确定性脚本分工、治理自身接受治理。逐项出处和吸纳边界见[吸纳清单](INTAKE-CATALOG.md)。

门禁分三层：

1. **仓内结构约束**：活文档/模板/引用、域形状、重复路径、过程稿被跟踪、派生物漂移、规范与检查入口一致。须说明扫描范围并有正/负例、空输入和非预期错误测试。
2. **项目行为/契约证据**：需求和风险对应的测试、真实接口/模型/环境检查、必要生成管线。通用模板定义接口与职责，具体栈适配提供实现。
3. **语义审查与裁决**：系统边界、跨域职责、图关系、需求充分性、测试断言质量、事实/目标冲突与安全人工复审。不能由registry、hash、计数或Agent自填状态替代。

同一实现可供人工/hook/CI调用，但文件存在不证明已安装或执行。源CI链也未被证实完整调用本地门禁；不得把“机器入口存在”写成“所有环节强制生效”。

## 9. 现有v2成果如何处理

| 处置 | 内容 | 理由 |
|---|---|---|
| 保留 | v1资产/golden、安全装配/owner、命名、无静默覆盖、检查结果分类、真实命令包装、显式升级与备份、现场保护、薄平台入口 | 有效支撑工具，不是本轮全部白做；不改变其已验证范围 |
| 围绕新模型改造 | AGENTS、conductor/dev-flow、文档/研发规则、系统/域模板、完整性与完成判定 | 当前无法定位长期设计或证明持续收敛，不能只补标题 |
| 停止扩张 | 更多authority registry、UUID状态、自动绑定、hash/disposition和语言检查器 | 先用真实设计演进找最小必要机制，避免让新JSON成为另一知识中心 |
| 待整体审阅替换 | JSON作为生命周期/设计权威的定位；living-specs可关闭；永久每任务设计档；02-design设计/账本混放；强制全部开发使用自建任务状态机 | 属于方案层偏差，不宜无边界叠修 |
| 保留现场后再决定迁移 | 原研究、实施报告、过程文件、旧设计、未提交代码 | 不自动删除；需要归并时给内容/路径/引用映射及承接验证 |

## 10. 新验收：连续演进，而非工具自测

| 编号/场景 | 必须观察到的真实结果 |
|---|---|
| A1 首次设计与定位 | 有填实的系统设计及至少两个职责明确域；新会话不靠旧聊天能找到正确权威 |
| A2 同域连续三次需求 | 同一个spec就地演进；当前行为清楚、旧决策有取代关系；不增加三套长期spec/plan/implementation |
| A3 跨域公共契约变化 | 找出所有受影响域和系统不变量；公共规则一个owner，事实资产同步，不只回刷最初选的域 |
| A4 已批准但未实现 | 同一活spec清楚标明目标与实现/验证状态，任务稿不临时取代设计权威 |
| A5 测试绿但违反设计 | 注入语义错误或画错依赖方向；即使结构/常规测试通过仍识别偏差并裁决，不能补note/hash放行 |
| A6 过程稿收敛与新检出 | 在独立测试副本仅提供共享快照，新会话能解释现行设计、理由与未完成条件；缺本地草稿明确恢复方式。真实工作区不删除 |
| A7 真实方法链与无工具路径 | 分别记录实际调用/版本/落点与未调用替代的完整产物；同域重入不产生新权威 |
| A8 实现中断和并行 | 本机恢复、换机恢复、多变更同域有明确界限；不依赖单active指针覆盖其他任务，保留用户改动 |
| A9 真实缺陷与学习 | 失败复现→修复→回归→根因/防复发→长期owner，未完成项不被报告吞掉 |
| A10 检查器故障与接入 | 空扫描、坏输入、缺工具、非预期退出不完整通过；未装hook/离线/不同OS如实记录，不自动引服务 |
| A11 域拆分/合并/废弃 | 职责和身份转移明确，原域指向接管，引用不悬空，历史不被清场 |
| A12 范围与长期增长 | Agent提出额外服务/表/抽象时必须溯源批准需求；多轮后设计依然可定位，过程稿不增长成第二套知识库 |
| A13 小项目裁剪与发布边界 | 内容可短但保留治理语义；未授权发布时停在开发验收，不自动Git/部署 |

原有工具测试继续保留，但不得用它们替代这些验收。代表性场景通过也只能证明对应样本，不证明所有中大型系统已长期规模化验证。

## 11. 重新排序的实施次序

1. **完整模型与填实例子**：先在模板维护仓建立明确的当前系统/域设计，区分已有实现和拟议能力，再抽出通用模板；不先造更多注册表。
2. **连续演进试点**：完成A1–A6的设计/行为对照，观察第二次、第三次变化后的文档成品与新增文件职责。
3. **真实方法调用及产物适配**：验证Spec Kit/superpowers实际落点、域复用、方法关系与无工具替代；不能虚构可用命令。
4. **最小机器约束**：依据试点暴露的具体失效点接检查；结构、行为、语义责任分开，具备坏例和执行接入证据。
5. **复用既有v2工具**：配置/装配/任务辅助/升级围绕已确定的设计模型整合；哪些状态机保留由其实际用途决定。
6. **兼容与升级审阅**：给现有文件owner、目标承接、保留/指针/移动建议和用户手改冲突；重大替换、归档、删除先交可审阅清单。

此顺序与原“先配置/状态机/门禁，最后可选域模板”相反。新实施链按本方案推进；具体实现/验证状态在长期域设计原位维护。

## 12. 已明确与待整体审阅的政策

已经明确，无需再向用户逐条求证：域spec长期维护、同域就地更新、设计与代码持续收敛、真实方法链、过程反膨胀、AGENTS只作入口/地图、不将工具计数当成功指标、不新增平台服务、不清理历史。

本方案推荐的整体政策：活spec承载已批准目标并标实现/验证状态；重型过程稿默认本地，短当前态承担必要跨机续接；已有授权内自主推进，重大目标变化/安全/外部动作保留明确裁决。具体路径、编号和schema是工程选择，不应把它们当新一轮用户问卷。

真正需要在整体方案及试点中验证的取舍：未提交/未共享工作的换机恢复程度、实际外部技能版本和产物可控性、哪些当前执行材料确需共享、历史结构的迁移承接范围。未知保持未知，不以源文档或Astra结论替代运行证据。
